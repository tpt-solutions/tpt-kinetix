# Live server load test, 2026-11-07

`tools/live-load-test.py` against `target/release/tpt-kinetix live` (release build of
this tree, default `live` options: 2 s segments, low-latency parts on). Each publisher
pushes one pre-made 320x180 VP9 WebM by stream copy, paced with `ffmpeg -re`. Each
viewer polls `track-0.m3u8` of one stream as fast as it can for 20 seconds. The server's
resident memory is sampled once a second.

Machine: Windows 11 (10.0.26200), one host running server, publishers and viewers.

## How to read this

- **These are floors, not capacity.** The viewers are Python threads on the same host,
  so the client shares the CPU and the GIL with the server. At 8x64 the client is the
  likely limit: throughput stops rising between 4x16 and 8x64 while latency grows.
- **The 1x1 row is client-bound.** A single viewer's p50 of 15.6 ms equals the Windows
  timer quantum, not server work; with 16 viewers the same server answers in under 4 ms.
  Do not read the 1x1 latency as the server's.
- **No request failed and no playlist was missing**, including while publishers were
  still running. The 404-before-first-segment path was not exercised, because the
  viewers start after a 3 s warm-up.
- **Memory stayed flat** (10–22 MiB) across all three runs.

Not measured: CPU per stream, remote viewers over a real network, and the
blocking-reload (`_HLS_msn`) path. Those need a client that can hold many blocking
requests open, which this script does not do.
