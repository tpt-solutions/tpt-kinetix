## Reading the units

A value with an `elem/s` or `B/s` unit is **throughput** (higher is better); a value with a time unit (`ms`, `us`, `s`) is a **duration** (lower is better). Benchmarks whose Criterion group declared no `Throughput` are recorded as durations, so compare those against each other by inverting the direction.

- `Melem/s` / `Kelem/s` — megapixels (resp. kilopixels) of luma processed per second for the 2D codecs, and megapixels of sample count per second for the lossless codec.
- `elem/s` on the realtime bench counts **slices** (64 per frame at the 8x8 grid), which is the latency-relevant unit rather than frames.
- `MiB/s` on the bitstream bench is raw payload bytes through `BitReader` / rANS.
- `Melem/s` on the volumetric bench counts 6 values per point (3 position components plus 3 colour samples).

## Notes on this snapshot

**This snapshot is not comparable to `baseline-2026-10-02.json`.** That is not a
hedge about machine drift — the older file was recorded against code that has
since been fixed, so for several crates it measures a decoder doing (almost) no
work.

`baseline-2026-10-02.json` was committed in `1a8623c` at 06:49 on 2026-10-02.
Eight and a half hours later the same day, `8291e0b` ("Add ffmpeg comparison
harness and fix codec bugs it surfaced") changed `src/` in **av1, bitstream,
lean, lossless, realtime, screen and vp9**, and was never followed by a
re-record. Comparing the two files directly:

| Bench | 10-02 | 10-03 | Appears as |
|:---|---:|---:|---:|
| `tpt-kinetix-screen/320x240/decode` | 1.1071 Gelem/s | 8.0094 Melem/s | **-99.3%** |
| `tpt-kinetix-realtime/320x240/decode` | 236.00 Melem/s | 12.466 Kelem/s | **-100.0%** |

A 134x "regression" that no same-session A/B ever saw, on code whose tests pass
and which measured 32% *faster* in the A/B that motivated the optimisation. The
bench definitions did not change (`screen_codec.rs` is untouched since
`1a8623c`), so the difference is in the library underneath: the old numbers
come from a decoder that was bailing out early instead of decoding.

The same confound inflates the *positive* deltas. `bitstream_rans/decode_noise`
appears to have gained 361%, but the Phase 3 A/B recorded before/after of
181 → 195 MiB/s for that crate. Quoting the cross-file delta would have
overstated the work by an order of magnitude.

**What to trust.** The per-change numbers in `todo-perf.md` and the commit
messages — each was measured same-session, A/B'ing alternating builds. This
file is the reference point for *future* comparisons. Against untouched crates
(face, volumetric, demux, mux, pipeline) it still shows a mean of -3.3% and a
range of -24.6%..+29% with zero code change, which is a fair estimate of this
machine's cross-session spread; that is why same-session A/B, not
baseline-to-baseline, is the method used throughout Phase 3.

### Methodology

- ffmpeg is timed with `-benchmark -f null -` (the `rtime=` figure: wall time inside the transcode loop, excluding process spawn); Kinetix is timed in-process, best of the recorded runs, fresh decoder per run.
- Decode correctness is verified **before** timing: Kinetix planes must be byte-identical to the reference decoder's, otherwise the ratio column reads `n/a (unverified)`.
- Corpus: ffmpeg-generated `testsrc` clips (cached in `target/perf-corpus/`, regenerated when the generator arguments change) plus the committed AV1 FATE fixtures.
- Re-run after any optimisation change; numbers are only comparable within one machine and toolchain (see the Phase 0 caveat above).
